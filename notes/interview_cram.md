## MOVE SEMANTICS — повністю

### Всі п'ять спеціальних функцій (rule of five)
Клас з ресурсом (сирий вказівник/handle) типово потребує всіх п'ять:

```cpp
class Buffer {
public:
    Buffer() : data(new int[100]), size(100) {}                    // конструктор

    Buffer(const Buffer& o) : data(new int[o.size]), size(o.size) { // copy ctor
        std::copy(o.data, o.data + size, data);                     // deep copy
    }

    Buffer& operator=(const Buffer& o) {                            // copy assign
        if (this == &o) return *this;         // self-assignment guard!
        int* newData = new int[o.size];       // спочатку виділити нове
        std::copy(o.data, o.data + o.size, newData);
        delete[] data;                        // потім звільнити старе
        data = newData; size = o.size;
        return *this;
    }

    Buffer(Buffer&& o) noexcept : data(o.data), size(o.size) {      // move ctor
        o.data = nullptr; o.size = 0;         // джерело в безпечний стан
    }

    Buffer& operator=(Buffer&& o) noexcept {                        // move assign
        if (this == &o) return *this;         // self-assignment guard
        delete[] data;                        // звільнити своє старе
        data = o.data; size = o.size;         // забрати чуже
        o.data = nullptr; o.size = 0;         // джерело в безпечний стан
        return *this;
    }

    ~Buffer() { delete[] data; }                                    // деструктор
private:
    int* data; size_t size;
};
```

Ключові відмінності copy vs move версій:
- **copy ctor/assign**: виділяє нову пам'ять, копіює елементи один за одним — O(n).
- **move ctor/assign**: краде вказівник джерела напряму — O(1), джерело лишає в безпечному (nullptr) стані.
- **self-assignment guard** (`if (this == &o) return *this;`) — критично для assignment-операторів (і copy, і move): `a = a;` або `a = std::move(a);` не повинні зламати об'єкт.
- **порядок операцій у copy assign**: спочатку виділити нове й скопіювати, і лише потім звільнити старе — якщо `new` кине виняток на середині, старий стан лишається валідним (strong exception guarantee). Це називають copy-and-swap idiom у повнішому вигляді.
- **чому move-версії `noexcept`**: `std::vector` під час реалокації використовує move тільки якщо він `noexcept` — інакше про exception-safety підстраховується копією (щоб не лишити вектор у напівпошкодженому стані при кинутому винятку в середині move).

### Оголосив move ctor → copy видаляється
Якщо клас оголошує **хоч одну** з move-версій — компілятор автоматично видаляє implicit copy ctor/assign. Клас стає move-only (як `std::unique_ptr`, `std::thread`, `std::ifstream`).

### std::move — механіка
`std::move(x)` = `static_cast<T&&>(x)`. Нічого не рухає сам — лише каже overload resolution "обери move-версію". Без move-версії — мовчки впаде на copy.

### Forwarding references + std::forward (часто питають разом з move)
`T&&` у контексті **template-параметра** (не в конкретному класі) — це не rvalue-посилання, а **universal/forwarding reference**: приймає і lvalue, і rvalue, і "запам'ятовує" яким саме.

```cpp
template <typename T>
void wrapper(T&& arg) {
    inner(std::forward<T>(arg)); // передає arg далі зі збереженням lvalue/rvalue-ності
}
```
`std::forward` — умовний `std::move`: рухає, тільки якщо оригінальний аргумент був rvalue. Без цього — proxy-функції завжди копіювали б, навіть коли викликач передав тимчасовий об'єкт.

### lvalue vs rvalue (база, без зайвого)
lvalue — має ім'я/адресу, живе довше виразу (змінна). rvalue — тимчасове значення без стійкої адреси (літерал, результат виразу, `std::move(x)`). Move-конструктор приймає rvalue, бо тимчасовий об'єкт однаково скоро помре — можна безкарно вкрасти його ресурс.

## STL / std:: — контейнери й утиліти

### Контейнери — коли який
| Контейнер | Структура | push_back | доступ за індексом | пошук |
|---|---|---|---|---|
| `std::vector` | суцільний масив | amortized O(1) | O(1) | O(n) |
| `std::deque` | масив блоків | O(1) з обох кінців | O(1) | O(n) |
| `std::list` | двозв'язний список | O(1) | немає | O(n) |
| `std::map` | red-black tree, впорядкований | — | — | O(log n) |
| `std::unordered_map` | хеш-таблиця | — | — | O(1) середнє, O(n) найгірше |
| `std::set`/`unordered_set` | те саме що map, без значення | — | — | log n / O(1) |

`vector` — дефолтний вибір, доки не доведено що треба інше (cache locality, суцільна пам'ять). `map` vs `unordered_map`: бери unordered якщо не треба сортований порядок і важлива швидкість — O(1) в середньому проти O(log n).

### push_back vs emplace_back
`push_back(x)` — створює тимчасовий об'єкт і копіює/рухає його в контейнер.
`emplace_back(args...)` — конструює об'єкт **напряму в пам'яті контейнера**, без проміжного тимчасового об'єкта. Для важких об'єктів — економія однієї copy/move-операції.

### Ітератори
Категорії: forward (`list`, `forward_list`), bidirectional (`list`, `map`), random access (`vector`, `deque`, `array`) — визначає, які операції з ітератором доступні (`it + 5` працює лише для random access).
Інвалідація ітераторів — критично для `vector`: `push_back` при реалокації інвалідує **всі** ітератори/посилання/вказівники на елементи.

### std::optional / std::variant / std::any
`std::optional<T>` — "може бути значення, а може ні", заміна `T*`/спеціальних сентинел-значень без heap-алокації.
`std::variant<A,B,C>` — типобезпечний union, знає який з типів зараз всередині, доступ через `std::get`/`std::visit`.
`std::any` — тримає будь-який тип, з рантайм type-check (аналог `std::function`'s type erasure, але для даних, не callable).

### std::string_view
Невладіючий (non-owning) погляд на рядок — вказівник + довжина, без копіювання/алокації. Дешевше передавати `std::string_view` замість `const std::string&`, коли не треба володіти даними. Небезпека: не тримає власника — dangling, якщо оригінальний рядок помре раніше.

### std::pair / std::tuple
Групування кількох значень без окремого struct. `std::tie`/structured bindings (`auto [a, b] = pair;`) для розпаковки.

## БАГАТОПОТОКОВІСТЬ — повністю

### std::thread — база
```cpp
std::thread t([]{ /* робота */ });
t.join();   // чекати завершення (блокує викликача)
// або
t.detach(); // відв'язати, потік живе сам по собі — небезпечно, важко контролювати lifetime
```
Незʼєднаний (`joinable() == true`) `std::thread`, який виходить зі скоупу без `join()`/`detach()` — викликає `std::terminate()`.

### mutex-варіанти
- `std::mutex` — базовий, не рекурсивний (повторний lock у тому ж потоці — deadlock/UB).
- `std::recursive_mutex` — той самий потік може лочити повторно (лічильник).
- `std::lock_guard<std::mutex>` — RAII-обгортка, лочить у конструкторі, розлочує в деструкторі, **не можна** розлочити достроково.
- `std::unique_lock<std::mutex>` — те саме, але гнучкіший: можна розлочити достроково, передати в `condition_variable`, відкласти лок (`std::defer_lock`).

### race condition vs data race
**Race condition** — результат залежить від непередбачуваного порядку виконання потоків (ширше поняття, не завжди UB).
**Data race** — конкретний випадок: два потоки одночасно звертаються до **однієї пам'яті**, хоча б один запис, без синхронізації — це завжди **undefined behavior** за стандартом C++ (не просто "неправильний результат").

### deadlock vs livelock
Deadlock — потоки взаємно заблокували один одного назавжди (чекають ресурс, який тримає інший). Фікс: єдиний порядок захоплення локів, або `std::lock(m1, m2)` для атомарного захоплення кількох одразу.
Livelock — потоки не заблоковані, але постійно "уступають" один одному і не прогресують (рідше питають, але варто знати термін).

### std::atomic
Апаратно-атомарні операції без mutex — дешевше для простих незалежних значень (лічильники, флаги).
Memory order (якщо копнуть глибше): `memory_order_relaxed` (тільки атомарність, без гарантій порядку) → `acquire`/`release` (синхронізація між потоками навколо конкретної змінної) → `seq_cst` (найсуворіший, дефолтний, глобальний порядок для всіх). У 95% випадків достатньо дефолтного `seq_cst`, просто знати що не всі atomic-операції рівні за "суворістю".

### condition_variable — producer/consumer
```cpp
std::mutex m;
std::condition_variable cv;
std::queue<int> q;

void producer() {
    { std::lock_guard<std::mutex> lock(m); q.push(42); }
    cv.notify_one();
}
void consumer() {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return !q.empty(); }); // спить, поки предикат false
    int v = q.front(); q.pop();
}
```
`wait()` атомарно розлочує mutex і засинає; при `notify` — прокидається, перезахоплює lock, перевіряє предикат (захист від spurious wakeup).

### std::async / std::future
```cpp
std::future<int> f = std::async(std::launch::async, [] { return compute(); });
int result = f.get(); // блокує, чекає результат (або кидає виняток, якщо в задачі був throw)
```
Простіший спосіб отримати результат з фонового потоку без ручного mutex/condition_variable для однієї передачі значення.

### Qt-специфіка з потоками
Антипатерн: успадкувати `QThread`, перевизначити `run()`.
Правильно: worker-`QObject` + `worker->moveToThread(thread)` + сигнали/слоти.
`Qt::AutoConnection` (дефолт) — якщо той самий потік, виклик прямий (`DirectConnection`), інакше через чергу подій (`QueuedConnection`, копіює аргументи, виконує в потоці-власнику). `QMutex`, `QWaitCondition` — Qt-аналоги `std::mutex`/`condition_variable`.

## std::function — детально

Проблема: кожна лямбда має унікальний, згенерований компілятором тип — звичайний вказівник на функцію не може тримати лямбду, яка щось захопила. `std::function<int()>` вирішує це через **type erasure**: у момент присвоєння компілятор генерує під конкретний тип три функції ("викликати", "скопіювати", "знищити"), і `std::function` зберігає вказівники на них + самі дані.

Де лежать дані: малий captured-стан — у внутрішньому буфері самого `std::function` (Small Buffer Optimization, типово ~16 байт, без алокації). Великий — одна heap-алокація, `std::function` тримає вказівник туди.

```cpp
std::function<void()> fn;
if (fn) fn();                 // порожній fn → operator bool() == false
else std::cerr << "empty";    // виклик порожнього кинув би std::bad_function_call
```

Ціна: виклик `fn()` — непрямий виклик через вказівник (як virtual dispatch), компілятор не може заінлайнити (на відміну від template-параметра, де тип відомий на етапі компіляції).

`std::move_only_function` (C++23) — звичайний `std::function` вимагає copyable callable (сам він copyable тип); лямбду з `unique_ptr` у capture в нього не покласти — для цього і додали move-only варіант.

## Smart pointers — детально

`std::unique_ptr<T>` — одноосібне володіння, **move-only** (копіювання видалене), нульовий runtime overhead проти сирого вказівника (той самий розмір, деструктор викликає `delete` автоматично).

`std::shared_ptr<T>` — reference counting: кожна копія інкрементує **атомарний** лічильник посилань, деструктор декрементує, об'єкт видаляється коли лічильник → 0. Дорожчий за `unique_ptr` (розмір вказівника ×2 — сам об'єкт + control block з лічильниками, атомарні операції на кожну копію/знищення).

`std::weak_ptr<T>` — "не володіюче" посилання на об'єкт під `shared_ptr`, не тримає його живим, не заважає видаленню. Потрібен, щоб розірвати цикл володіння (`shared_ptr` A ↔ B один на одного — обидва ніколи не звільняться без `weak_ptr` на одному з боків).

Коли який: `unique_ptr` — дефолт, якщо володіння одноосібне (найчастіше). `shared_ptr` — коли реально кілька власників з непередбачуваним часом життя. `weak_ptr` — спостерігач без володіння (наприклад, кеш чи callback-и, що не повинні продовжувати життя об'єкта).

## RAII

Resource Acquisition Is Initialization: ресурс (пам'ять, файл, mutex-лок, сокет) захоплюється в конструкторі, звільняється в деструкторі. Прив'язує час життя ресурсу до часу життя об'єкта — і, найголовніше, деструктор все одно відпрацює навіть якщо між захопленням і плановим звільненням кинуто виняток (stack unwinding викликає деструктори всіх локальних об'єктів на шляху нагору).

```cpp
void process() {
    std::lock_guard<std::mutex> lock(m);  // лок береться тут
    doSomethingThatMayThrow();            // якщо кине виняток —
}                                          // lock_guard все одно розлочить у деструкторі
```

Приклади в STL: `std::lock_guard`/`unique_lock` (mutex), `std::unique_ptr`/`shared_ptr` (пам'ять), `std::ifstream`/`ofstream` (файл), `std::vector` (буфер на купі).

## const-correctness — const T& vs T&&

`const T&` — посилання, яке не можна змінити через нього; біндиться до **всього** (lvalue і rvalue), нульова ціна копіювання (просто передає адресу).
`T&&` — rvalue-посилання, приймає **тільки** тимчасові об'єкти/явно-переміщені (`std::move(x)`); всередині функції можна безкарно "красти" ресурс, бо джерело однаково скоро помре.
`T&` (без const) — приймає тільки lvalue, дозволяє змінювати оригінал через посилання — використовується коли функція навмисно повинна модифікувати аргумент викликача.

Метод класу, позначений `const` (`int value() const`) — гарантує, що не змінює стан об'єкта (не може викликати не-const методи, не може писати в member-и, окрім `mutable` полів). Дозволяє викликати метод на `const T&`.

## Undefined behavior — класичні приклади

- **Dangling reference/pointer** — повернути посилання/вказівник на локальну змінну функції; вона знищується при виході, будь-яке подальше звернення — UB (класичний приклад: лямбда з `[&x]`, де `x` — локальна змінна функції, що повертає цю лямбду).
- **Data race** — два потоки одночасно читають/пишуть одну пам'ять без синхронізації, хоча б один запис — завжди UB за стандартом, не просто "неправильний результат".
- **Use-after-move без переініціалізації, якщо клас це не гарантує** — читати стан moved-from об'єкта безпечно (валідний, хоч і невизначений стан), а от розраховувати на конкретний вміст — логічна помилка.
- **Buffer overflow** — вихід за межі масиву/вектора (`v[v.size()]`, на відміну від `v.at()`, який кине виняток) — UB, не гарантована помилка сегментації.
- **Signed integer overflow** — на відміну від unsigned (де overflow добре визначений — wraparound), переповнення `int` — UB, компілятор може оптимізувати код виходячи з припущення "цього не станеться".

## Qt signal/slot — детально

Meta-Object Compiler (moc) — окремий крок збірки, який для кожного класу з `Q_OBJECT` генерує додатковий `.cpp` (`moc_ClassName.cpp`) з таблицею сигналів/слотів і функцією `qt_metacall`. Це і є причина, чому Qt-класи не можна юзати з голим CMake без moc-кроку — звичайний C++ компілятор нічого не знає про `signals:`/`slots:`.

`emit signal(args)` — шукає в таблиці всі підключені слоти й викликає їх:
- **DirectConnection** — прямий синхронний виклик (той самий потік).
- **QueuedConnection** — аргументи копіюються, подія кладеться в чергу event loop-у потоку-власника слота, виконується асинхронно.
- **AutoConnection** (дефолт) — Qt сам вирішує Direct чи Queued, залежно від того, чи слот у тому ж потоці.

`QObject` parent-child (не плутати з C++ спадкуванням) — `QObject`, створений з `parent`, автоматично видаляється в деструкторі батька. Дозволяє не тримати ручний `delete` для UI-дерева/дочірніх об'єктів.

## TCP vs UDP

TCP — з гарантією доставки, порядку пакетів, контролем перевантаження (congestion control) і встановленням з'єднання (handshake) — дорожчий, є затримки на ретрансміт втрачених пакетів.
UDP — без жодних гарантій (доставки, порядку), мінімальний overhead, без з'єднання (connectionless) — просто шле пакети.

Чому MAVLink/телеметрія типово UDP: втратити один пакет позиції (раз на секунду) не критично — прилетить наступний, свіжіший. А чекати TCP-ретрансміт застарілих даних гірше, ніж просто пропустити й отримати актуальніші. Для критичних команд (наприклад, arm/disarm) поверх UDP іноді додають власний рівень підтвердження (ACK) — MAVLink має вбудовані message IDs і опціональні sequence numbers саме для цього.

## Linux — база

Процес — окремий адресний простір (ізольована віртуальна пам'ять), потік — виконання всередині процесу, **ділить** пам'ять/файлові дескриптори з іншими потоками того ж процесу (тому race condition можлива між потоками, але не напряму між процесами — там треба IPC).

Інструменти:
- `ps`/`top`/`htop` — список процесів, використання CPU/пам'яті.
- `gdb` — дебагер: breakpoints, `bt` (backtrace), інспекція змінних.
- `strace` — трасування системних викликів процесу (що саме він читає/пише/відкриває).
- `ldd` — які динамічні бібліотеки (.so) підключає бінарник.
- `valgrind` — пошук memory leaks/некоректного доступу до пам'яті (згадати як інструмент, якщо спитають про пошук memory leaks).
